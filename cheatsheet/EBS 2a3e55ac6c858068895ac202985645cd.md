## 🧭 **Purpose**

**Amazon Elastic Block Store (EBS)** provides **block-level storage** for use with **EC2 instances**.

It’s designed for **high availability**, **low latency**, and **persistent storage** that remains available even after an instance is stopped or terminated (unless deleted on termination).

---

## ⚙️ **Key Features**

| Feature | Description |
| --- | --- |
| **Block Storage** | Provides raw storage volumes that attach to EC2 instances. |
| **Persistent Storage** | Data persists independently of the instance lifecycle. |
| **Volume Types** | Different types optimized for performance or cost (GP3, IO2, ST1, SC1). |
| **Snapshots** | Point-in-time backups stored in S3 (incremental). |
| **Encryption** | Data at rest encrypted with **KMS**; supports encryption by default. |
| **Multi-Attach** | Certain IO1/IO2 volumes can attach to multiple EC2 instances in the same AZ. |
| **Elastic Volumes** | Modify type, size, or IOPS without downtime. |
| **Fast Snapshot Restore (FSR)** | Reduces initialization time when restoring from snapshots. |
| **Regional Availability** | Volumes are **AZ-scoped** but snapshots are **Region-scoped**. |
| **Performance Metrics** | Monitored via CloudWatch for throughput and latency. |

---

## 🏗️ **Common Exam Use Cases**

| Scenario | Recommended Solution |
| --- | --- |
| Run boot or OS volume for EC2 | Use **EBS GP3 or GP2** |
| Run transactional workloads (databases) | Use **IO2 or IO2 Block Express** for high IOPS consistency |
| Store large sequential data (e.g., logs, backups) | Use **Throughput Optimized (ST1)** |
| Store infrequently accessed cold data | Use **Cold HDD (SC1)** |
| Back up data for DR or migration | Create **Snapshots** (incremental backups to S3) |
| Quickly replicate a volume across Regions | Copy **EBS Snapshots** between Regions |
| Scale volume size or performance | Use **Elastic Volumes** to modify live |
| Improve restore performance | Enable **Fast Snapshot Restore (FSR)** |
| Encrypt data transparently | Use **KMS-integrated encryption** |
| Attach one volume to multiple EC2 instances | Use **Multi-Attach** with **IO1/IO2** (same AZ) |

---

## 🔐 **Security Considerations**

- **Encryption at rest** is available by default (using KMS-managed keys).
- Encrypt **new volumes, snapshots, and restored copies** automatically.
- Use **IAM policies** to restrict snapshot sharing.
- Snapshots can be shared across accounts or made public (use caution).
- Data in transit between EC2 and EBS is automatically encrypted.
- Audit activity via **CloudTrail**.

---

## 💲 **Pricing Model**

- Charged for **provisioned GB per month**.
- **IOPS and throughput** billed separately for performance-optimized volumes.
- **Snapshots** charged by data stored in S3 (incremental basis).
- **Fast Snapshot Restore** and **Multi-Attach** add additional cost.

**Volume Type Summary:**

| Type | Description | Use Case |
| --- | --- | --- |
| **gp3** | General-purpose SSD; baseline 3,000 IOPS, burstable. | Default for most workloads. |
| **io2/io2 Block Express** | High-performance SSD with up to 256,000 IOPS. | Databases, mission-critical workloads. |
| **st1** | HDD optimized for throughput (500 MB/s). | Log processing, streaming data. |
| **sc1** | Cold HDD for rarely accessed data. | Archive or infrequent workloads. |

---

## 🔗 **Integration Patterns**

- **EC2** → Primary compute attachment.
- **CloudFormation** → Infrastructure provisioning with EBS definitions.
- **Data Lifecycle Manager (DLM)** → Automate snapshot creation/retention.
- **Backup** → Managed EBS backups via **AWS Backup**.
- **KMS** → Encryption management.
- **CloudWatch** → Volume metrics monitoring.

---

## 🧠 **Exam Tips**

✅ EBS = **block storage**; S3 = **object storage**.

✅ Volumes are **AZ-specific**, but **snapshots are Regional**.

✅ **gp3** is the new default (not gp2).

✅ **IO2 Block Express** for high IOPS (>64,000).

✅ Always create **snapshots before terminating** instances to retain data.

✅ **Elastic Volumes** = modify size/type without downtime.

✅ **Multi-Attach** supports **IO1/IO2** volumes for shared access (same AZ only).

✅ Snapshots are **incremental** and stored in **S3**.

✅ Use **FSR** to reduce restoration time for latency-sensitive workloads.

## 🏁 **Real-World Example**

**Scenario:**

A financial analytics application requires high-performance, durable storage for databases and low-cost archival for logs.

**Solution:**

- Use **IO2 volumes** for primary database EC2 instances (consistent latency).
- Schedule daily **snapshots** with **DLM** for automated backups.
- Store logs on **ST1** volumes to optimize throughput at lower cost.
- Enable **KMS encryption** for all volumes and snapshots.

**Outcome:**

Highly available, performant, and cost-optimized block storage solution with automated recovery and compliance-ready encryption.
