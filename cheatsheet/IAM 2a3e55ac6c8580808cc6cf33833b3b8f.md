# **AWS Identity and Access Management (IAM) – Study Sheet**

*(Centrally manage access to AWS resources securely and at scale)*

**Exam Domains:**

- Design Secure Architectures
- Design Cost-Optimized Architectures

---

## 🧭 **Purpose**

**AWS Identity and Access Management (IAM)** enables you to **securely control access** to AWS resources for users, groups, and services.

It defines **who can access what**, **from where**, and **under what conditions**, enforcing the **principle of least privilege** across your AWS environment.

---

## ⚙️ **Key Features**

| Feature | Description |
| --- | --- |
| **Users, Groups, Roles, and Policies** | Core IAM entities for access management. |
| **IAM Policies (JSON)** | Define permissions (“allow” or “deny”) for actions on resources. |
| **IAM Roles** | Grant temporary permissions to AWS services, applications, or users (no passwords or keys). |
| **IAM Groups** | Simplify permission management for multiple users. |
| **Temporary Security Credentials** | Provided via **STS (Security Token Service)**. |
| **IAM Policy Simulator** | Test policies before applying them. |
| **Service-Linked Roles** | Automatically created roles for AWS services. |
| **Access Analyzer** | Detects overly broad access policies and external sharing. |
| **Managed vs Inline Policies** | Managed = reusable; Inline = unique per entity. |
| **IAM Identity Center (successor to AWS SSO)** | Centralized access management for multi-account organizations. |
| **MFA (Multi-Factor Authentication)** | Adds a second layer of authentication for users and root accounts. |

---

## 🏗️ **Common Exam Use Cases**

| Scenario | Recommended Solution |
| --- | --- |
| Grant EC2 instance access to S3 securely | Attach an **IAM Role** to the instance |
| Allow Lambda to access DynamoDB | Assign a **Lambda Execution Role** |
| Limit user permissions to a specific bucket | Create a **resource-based S3 policy** |
| Share access between AWS accounts | Use **Cross-Account Roles** and **STS AssumeRole** |
| Prevent accidental deletions by admins | Add explicit **“Deny” statements** in IAM policies |
| Audit permissions for compliance | Use **IAM Access Analyzer** |
| Centrally manage user access to multiple accounts | Use **IAM Identity Center (AWS SSO)** |
| Enforce MFA for console access | Require **MFA on root and IAM users** |
| Automatically rotate credentials | Use **Access Keys rotation policies** |
| Troubleshoot access issues | Use **IAM Policy Simulator** and **CloudTrail logs** |

## 🔐 **Security Considerations**

- Enforce **MFA** for root and IAM users.
- Never use the **root account** for daily operations.
- Follow **least privilege**: grant only the permissions required.
- Rotate **access keys** regularly.
- Use **Roles** instead of **access keys** for services.
- Use **Condition keys** (e.g., `aws:SourceIp`, `aws:MultiFactorAuthPresent`) for fine-grained access control.
- Log all access attempts with **CloudTrail**.
- Use **Service Control Policies (SCPs)** in AWS Organizations for multi-account governance.
- Use **IAM Access Analyzer** to identify public or cross-account access risks.

## 💲 **Pricing Model**

- **IAM is free of charge.**
- You only pay for:
    - **MFA device** (if using hardware token)
    - **Services that IAM controls access to**
    - Optional logging/monitoring (CloudTrail, Config)

---

## 🔗 **Integration Patterns**

- **EC2 / Lambda / ECS:** Access AWS APIs using IAM roles.
- **CloudTrail:** Track IAM events (login, policy changes).
- **Organizations + SCPs:** Manage access across multiple accounts.
- **KMS / S3 / SNS:** Use resource-based policies.
- **IAM Identity Center:** Centralized user management and SSO access.

---

## 🧠 **Exam Tips**

✅ **IAM = least privilege, identity federation, and roles over keys.**

✅ Root user should only be used for **initial setup** and **account recovery**.

✅ **Roles** = temporary access; **Users** = long-term identities.

✅ **Policies** are evaluated with this order:

1. Explicit Deny
2. Explicit Allow
3. Implicit Deny
    
    ✅ Use **IAM Access Analyzer** to find unintended access.
    
    ✅ **STS AssumeRole** allows cross-account temporary access.
    
    ✅ Use **Condition keys** for context-aware security (IP range, time, MFA).
    
    ✅ IAM is **global**, not regional.
    
    ✅ Monitor permissions drift using **AWS Config** or **IAM Access Advisor**.

## 🏁 **Real-World Example**

**Scenario:**

A fintech company needs to allow its EC2 instances to upload logs to S3 securely without embedding credentials.

**Solution:**

- Create an **IAM Role** with an inline policy granting `s3:PutObject` to the log bucket.
- Attach the role to the EC2 instance.
- Enable **CloudTrail** to monitor API calls.
- Enforce **MFA** for admin accounts and restrict console logins by IP address.

**Outcome:**

Secure, auditable, and scalable access management without storing long-term credentials on instances.
